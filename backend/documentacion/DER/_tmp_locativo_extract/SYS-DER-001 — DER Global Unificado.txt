INTEGRACIÓN TOTAL DEL SISTEMA 
DER GLOBAL UNIFICADO 
Sistema de gestión inmobiliaria con motor financiero integrado 
 
1. Objetivo de esta etapa 
Esta etapa tiene por objeto construir la visión global unificada del sistema, integrando: 
 el DER del dominio transaccional ya cerrado 
 el DER del dominio administrativo ya cerrado 
La integración tiene que resolver: 
1. cómo conviven ambos dominios 
2. dónde se enlazan 
3. qué entidades permanecen separadas 
4. qué relaciones interdominio existen 
5. cuáles son las reglas estructurales globales del sistema completo 
 
2. Principio rector de integración 
IG-001 
El dominio transaccional mantiene su cierre y no se altera. 
IG-002 
El dominio administrativo se monta sobre el transaccional por referencia, contexto, 
trazabilidad y control. 
IG-003 
No se fusionan entidades por comodidad. 

IG-004 
La integración global del sistema debe preservar la separación entre: 
 negocio 
 administración 
 seguridad 
 auditoría 
 configuración 
 sincronización 
IG-005 
La integración global debe seguir siendo compatible con: 
 multi-sucursal 
 multi-instalación 
 sincronización distribuida 
 motor financiero único 
 trazabilidad documental 
 trazabilidad operativa 
 
3. Macrodominios del sistema global 
El DER global queda organizado en dos macrodominios principales. 
3.1 Dominio transaccional 
Incluye lo ya cerrado en el proyecto: 
 inmobiliario 
 comercial / ventas 
 locativo 
 personas 
 documental 
 financiero 
 multi-sucursal operativo 
 sincronización transaccional 
 numeración documental 
3.2 Dominio administrativo 

Incluye lo ya cerrado en esta etapa: 
 usuarios 
 credenciales 
 sesiones 
 historial de acceso 
 roles y permisos 
 autorización 
 auditoría 
 configuración 
 parámetros 
 catálogos maestros administrativos 
 
4. Entidades puente entre ambos dominios 
La integración no se hace “en masa”. Se hace mediante entidades puente o ejes comunes. 
Los ejes globales de integración son: 
1. PERSONA 
2. SUCURSAL 
3. INSTALACION 
4. op_id / operación distribuida 
5. DOCUMENTO como objeto auditable 
6. relaciones y entidades transaccionales como objetos auditables 
7. USUARIO_PERSONA como puente opcional entre identidad técnica y persona del 
dominio 
 
5. Ejes globales de integración 
5.1 Eje PERSONA 
GI-P-001 
PERSONA pertenece al dominio transaccional. 
GI-P-002 
El dominio administrativo no redefine PERSONA. 
GI-P-003 

La relación entre identidad técnica y persona del dominio se resuelve exclusivamente 
mediante: 
 USUARIO_PERSONA 
GI-P-004 
No todo usuario requiere persona asociada. 
GI-P-005 
No toda persona requiere usuario asociado. 
Resultado 
PERSONA actúa como punto de enlace controlado, no como entidad absorbida por seguridad. 
 
5.2 Eje SUCURSAL 
GI-S-001 
SUCURSAL es entidad compartida de contexto global del sistema. 
GI-S-002 
En el transaccional, SUCURSAL participa como unidad operativa de negocio. 
GI-S-003 
En el administrativo, SUCURSAL participa como contexto de: 
 habilitación operativa de usuario 
 autorización contextual 
 sesión 
 auditoría 
 parametrización 
 historización 
GI-S-004 
Sucursal no se duplica entre dominios. 
Resultado 
SUCURSAL es uno de los principales ejes comunes globales del sistema. 
 
5.3 Eje INSTALACION 
GI-I-001 
INSTALACION pertenece al modelo técnico-operativo global del sistema. 

GI-I-002 
INSTALACION no se fusiona con SUCURSAL. 
GI-I-003 
INSTALACION actúa como origen técnico de operaciones, sesiones, auditoría y sincronización. 
GI-I-004 
Toda acción técnica auditable relevante debe poder reconstruirse por instalación. 
Resultado 
INSTALACION es el eje común entre: 
 acceso 
 auditoría 
 sincronización 
 operación distribuida 
 
5.4 Eje op_id / operación distribuida 
GI-O-001 
El sistema global conserva el criterio de sincronización basado en operaciones. 
GI-O-002 
El dominio administrativo debe poder enlazarse conceptualmente con op_id. 
GI-O-003 
La auditoría administrativa soporta op_id. 
GI-O-004 
La integración global debe permitir reconstruir una misma operación a través de: 
 entidades transaccionales afectadas 
 eventos de auditoría 
 instalación emisora 
 contexto de usuario si existió 
Resultado 
op_id queda como eje transversal entre transaccional, administrativo y sincronización. 
 
5.5 Eje DOCUMENTO 
GI-D-001 

DOCUMENTO pertenece al dominio transaccional y sigue siendo independiente del usuario. 
GI-D-002 
El dominio administrativo no redefine DOCUMENTO. 
GI-D-003 
DOCUMENTO puede ser objeto auditado mediante: 
 EVENTO_AUDITORIA 
 OBJETO_AUDITADO 
Resultado 
DOCUMENTO es entidad transaccional auditada, no entidad administrativa.

B.1: MODELO RELACIONAL GLOBAL MAESTRO DEL SISTEMA. 
Lo voy a dejar como una consolidación formal única, montada sobre dos decisiones ya 
cerradas: 
 el dominio transaccional quedó congelado con sus tablas reales confirmadas, sus 
polimorfismos aceptados y el criterio de que el alcance por sucursal se materializa solo 
en desarrollo_sucursal y terreno_sucursal, heredándose al resto de las entidades 
derivadas. Además, el cierre físico refinado eliminó cuenta_corriente y 
subcuenta_financiera como tablas base obligatorias, dejando a relacion_generadora 
como raíz física del circuito financiero. 
 el dominio administrativo quedó cerrado con 31 entidades de cierre, incorporando al 
núcleo definitivo DENEGACION_EXPLICITA, OPERACION_AUDITORIA, 
PARAMETRO_OPCION y JERARQUIA_ITEM_CATALOGO.

Este modelo relacional global: 
 sí unifica tablas, PK, FK y ejes de integración 
 no cierra todavía: 
o tipos físicos exactos 
o índices finales 
o CHECK definitivos 
o triggers 
o vistas/materialized views 
o estrategia final offline/sincronización fina 
o performance y particionamiento

 relacion_persona_rol (tipo_relacion, id_relacion) 
 documento_entidad (tipo_entidad, id_entidad) 
 emision_numeracion (tipo_entidad_emitida, id_entidad_emitida)

5. Ejes de integración física global 
5.1 Persona 

persona sigue siendo transaccional; usuario_persona es el puente controlado entre identidad 
técnica y sujeto del dominio. 
5.2 Sucursal 
sucursal es tabla común global. El transaccional la usa para alcance raíz (desarrollo_sucursal, 
terreno_sucursal, numeración), y el administrativo para habilitación, autorización, sesiones, 
auditoría, parámetros e historiales. 
5.3 Instalación 
instalacion es el eje técnico común global. La usan sincronización transaccional y también 
sesion_usuario, evento_auditoria, historiales y trazabilidad administrativa. 
5.4 op_id 
op_id queda físicamente naturalizado en sincronizacion_operacion y conceptualmente 
enlazado con evento_auditoria y operacion_auditoria. 
5.5 Objetos auditables 
objeto_auditado debe poder apuntar tanto a entidades administrativas como a entidades 
transaccionales, sin supertabla física transversal nueva. Eso mantiene coherencia con la 
decisión de sostener asociaciones polimórficas controladas.

8. Reglas globales de integración física 
RG-1 
No se crea una supertabla transversal única para “entidad del sistema”. Se mantienen 
polimorfismos controlados donde ya fueron aceptados. 
RG-2 
El alcance por sucursal se materializa solo en: 
 desarrollo_sucursal 
 terreno_sucursal 
y el resto hereda. 
RG-3 
Todo lo administrativo que requiera trazabilidad contextual debe poder enlazarse con: 
 usuario 

 sucursal 
 instalacion 
 op_id cuando corresponda. 
RG-4 
La identidad técnica (usuario) y la identidad de negocio (persona) permanecen separadas. 
RG-5 
relacion_generadora es la raíz física del circuito financiero; no depende de 
subcuenta_financiera materializada. 
RG-6 
sincronizacion_operacion es la tabla técnica maestra de operación distribuida y debe sostener 
idempotencia por op_id.

CRITERIOS FÍSICOS GLOBALES DEL ESQUEMA SQL DEL SISTEMA 
Esto fija las reglas con las que después vamos a escribir el DDL completo sin contradicciones 
entre bloques. 
 
1. Objetivo de esta etapa 
Definir los criterios físicos globales para que todo el esquema SQL quede consistente en: 
 nombres 
 PK 
 FK 
 columnas de control 
 vigencia 
 estados 
 unicidad 
 polimorfismos 
 auditoría técnica mínima 
 compatibilidad con sincronización distribuida 
Todavía no escribimos todas las tablas en SQL final. 
Primero congelamos las reglas físicas maestras. 
 
2. Convenciones globales de nombres 
2.1 Nombres de tablas 
Regla general: 
 singular 
 minúsculas 
 snake_case 
 sin prefijos artificiales 
Ejemplos: 
 persona 
 venta 
 contrato_alquiler 
 obligacion_financiera 

 usuario 
 evento_auditoria 
2.2 Nombres de PK 
Regla general: 
 id_<tabla> 
Ejemplos: 
 id_persona 
 id_venta 
 id_usuario 
 id_evento_auditoria 
2.3 Nombres de FK 
Regla general: 
 mismo nombre que la PK referenciada 
Ejemplos: 
 venta_objeto_inmobiliario.id_venta 
 usuario_persona.id_usuario 
 usuario_persona.id_persona 
2.4 Nombres de columnas booleanas 
Regla general: 
 es_* 
 permite_* 
 requiere_* 
 admite_* 
 puede_* 
Ejemplos: 
 es_default 
 es_valor_vigente 
 requiere_reset 
 admite_override 
2.5 Nombres de fechas de vigencia 
Regla general: 

 fecha_desde 
 fecha_hasta 
2.6 Nombres de timestamps operativos 
Regla general: 
 fecha_hora_* 
Ejemplos: 
 fecha_hora_inicio 
 fecha_hora_evento 
 fecha_hora_cambio 
 
3. Criterio global de claves primarias 
3.1 Tipo de PK 
Recomendación para todo el sistema: 
 BIGINT autoincremental como PK interna física 
Motivo: 
 simple 
 robusto 
 eficiente para FK 
 cómodo para SQLite en desarrollo y migración posterior a motor servidor 
3.2 Clave técnica externa 
Cuando haga falta identificador funcional o portable, se agrega columna separada: 
 codigo_* 
 uuid_* PENDIENTE si se quiere universalizar para sincronización 
3.3 Decisión congelada 
La PK física del esquema será, por defecto: 
 BIGINT PRIMARY KEY 
 
4. Criterio global de claves foráneas 
4.1 Regla general 
Toda relación estructural real se materializa con FK física, salvo: 
 polimorfismos ya congelados 

 referencias lógicas a objetos auditados 
 referencias a entidad emitida/documentada en relaciones polimórficas 
4.2 FK obligatoria 
Si la relación conceptual es obligatoria, la FK será: 
 NOT NULL 
4.3 FK opcional 
Si la relación conceptual es opcional, la FK será: 
 NULL 
4.4 Política de borrado 
Regla general recomendada: 
 NO usar ON DELETE CASCADE por defecto 
 usar preferentemente: 
o RESTRICT 
o NO ACTION 
Motivo: 
 el sistema tiene muchísima historización 
 no conviene borrado en cascada en dominios jurídicos/financieros/auditables 
4.5 Excepciones posibles 
Solo podrían admitirse cascadas en tablas puramente auxiliares o de detalle técnico sin vida 
propia. 
 
5. Criterio global de columnas de estado 
5.1 Regla general 
Toda tabla que represente entidad viva de negocio o administración debe tener una columna 
de estado cuando el modelo conceptual la prevé. 
Ejemplos: 
 estado_usuario 
 estado_credencial 
 estado_sesion 
 estado_permiso 
 estado_catalogo 
5.2 Formato físico 

Recomendación: 
 VARCHAR controlado por catálogo/enum lógico 
 no usar enteros opacos sin semántica visible 
5.3 Catálogos de estado 
Los estados podrán resolverse luego por: 
 CHECK 
 catálogo maestro 
 ambos 
Según criticidad y reutilización. 
 
6. Criterio global de vigencia 
6.1 Regla general 
Toda relación o configuración historizable usa: 
 fecha_desde 
 fecha_hasta 
6.2 Semántica 
 fecha_desde inclusive 
 fecha_hasta nullable 
 fecha_hasta IS NULL = vigente 
6.3 Regla física 
No se sobrescribe un tramo de vigencia si el modelo exige historial. 
Se cierra el registro vigente y se inserta uno nuevo. 
6.4 Tablas típicas con vigencia 
 usuario_persona 
 usuario_sucursal 
 rol_seguridad_permiso 
 usuario_rol_seguridad 
 usuario_rol_sucursal 
 denegacion_explicita 
 valor_parametro 
 item_catalogo cuando aplique 

 jerarquia_item_catalogo cuando aplique 
 
7. Criterio global de unicidad 
7.1 Unicidad física simple 
Usar UNIQUE directo para: 
 codigo_usuario 
 nombre_usuario_login 
 codigo_permiso 
 codigo_rol_seguridad 
 codigo_catalogo_maestro 
 clave_tecnica_parametro 
7.2 Unicidad lógica por vigencia 
En relaciones históricas, la unicidad total no suele ser simple. 
Se resuelve con: 
 índice único parcial, si el motor lo soporta 
 o regla por trigger 
 o validación de aplicación + constraint auxiliar 
7.3 Casos típicos 
 una sola sucursal predeterminada vigente por usuario 
 una sola credencial principal activa por usuario/tipo 
 una sola asignación vigente equivalente usuario/rol/alcance 
 un solo valor vigente por parámetro y contexto 
 un solo item default activo por catálogo, salvo excepción 
 
8. Criterio global de auditoría técnica mínima de filas 
Esto es distinto de la auditoría funcional del dominio administrativo. 
8.1 Recomendación 
Definir un patrón mínimo transversal para tablas maestras y sensibles: 
 fecha_hora_alta 
 fecha_hora_ultima_modificacion PENDIENTE según motor 
 id_usuario_alta PENDIENTE en tablas administrativas 

 id_usuario_ultima_modificacion PENDIENTE 
8.2 Decisión práctica 
Para no contaminar de entrada todo el DDL, propongo: 
 no meter estas columnas en todas las tablas en la primera pasada 
 sí definirlas después solo en tablas administrativas y configurables si hace falta 
8.3 Regla congelada 
La trazabilidad principal del sistema sigue viviendo en: 
 auditoría funcional 
 historiales especializados 
 sincronización por operación 
No en columnas genéricas de fila como único mecanismo. 
 
9. Criterio global para polimorfismos 
Hay tres polimorfismos aceptados y no deben romperse. 
9.1 relacion_persona_rol 
Columnas: 
 tipo_relacion 
 id_relacion 
9.2 documento_entidad 
Columnas: 
 tipo_entidad 
 id_entidad 
9.3 emision_numeracion 
Columnas: 
 tipo_entidad_emitida 
 id_entidad_emitida 
9.4 Regla física 
Estos casos: 
 no tendrán FK clásica única 
 sí deberán tener: 
o CHECK de dominio de tipo 

o índice compuesto sobre (tipo_x, id_x) 
o validación por aplicación o trigger si se quiere integridad fuerte 
9.5 Regla de nombres 
Siempre mantener patrón: 
 campo discriminador tipo texto controlado 
 campo identificador numérico 
 
10. Criterio global para objetos auditados 
10.1 Tabla 
objeto_auditado 
10.2 Regla física 
No se crea una supertabla “entidad_sistema”. 
La auditoría de objetos se resuelve con: 
 nombre_entidad_auditada 
 id_registro_auditado 
 identificador_negocio_objeto nullable 
10.3 Motivo 
Evita rediseñar todo el sistema solo para soportar una auditoría transversal. 
 
11. Criterio global para sincronización distribuida 
11.1 op_id 
Debe existir un identificador operativo distribuido reutilizable. 
Recomendación: 
 op_id VARCHAR(...) NOT NULL en sincronizacion_operacion 
 nullable en tablas que solo lo referencian contextualmente, por ejemplo: 
o evento_auditoria 
o operacion_auditoria 
11.2 Idempotencia 
sincronizacion_operacion debe tener unicidad fuerte por op_id. 
11.3 Instalación emisora 
La operación distribuida debe poder reconstruirse por: 

 op_id 
 instalación origen 
 paquete/lote 
 fecha/hora 
 
12. Criterio global para sucursal e instalación 
12.1 Regla estructural 
sucursal e instalacion son tablas comunes globales. 
12.2 Regla física 
Toda tabla que requiera contexto técnico/operativo debe referenciar una o ambas 
explícitamente, según corresponda. 
12.3 Casos 
Solo sucursal 
 usuario_sucursal 
 usuario_rol_sucursal 
 numerador_documental 
Solo instalación 
 no suele haber muchos casos puros 
Ambas 
 sesion_usuario 
 evento_auditoria 
 historiales contextuales cuando corresponda 
 
13. Criterio global para parámetros 
13.1 Valores tipados 
valor_parametro usa columnas separadas: 
 valor_texto 
 valor_numero 
 valor_decimal 
 valor_booleano 
 valor_fecha 

 valor_fecha_hora 
13.2 Regla física 
Debe haber como máximo una columna materializada según el tipo de dato del parámetro. 
Eso luego se implementa con: 
 CHECK 
 trigger 
 validación de aplicación 
13.3 Contexto 
valor_parametro podrá tener: 
 sin sucursal ni instalación = global 
 sucursal y sin instalación = por sucursal 
 instalación, y eventualmente sucursal consistente = por instalación 
 
14. Criterio global para catálogos 
14.1 Catálogo maestro 
catalogo_maestro es cabecera reusable. 
14.2 Ítem 
item_catalogo identifica el valor concreto. 
14.3 Jerarquía 
jerarquia_item_catalogo solo aplica si el catálogo es jerárquico. 
14.4 Regla física 
Debe existir índice/constraint para evitar duplicados por: 
 catálogo + código de item 
14.5 Defaults 
La unicidad de default activo por catálogo probablemente requiera: 
 índice parcial 
 trigger 
 o control de aplicación 
 
15. Criterio global para documentos y numeración 
15.1 Documentos 

documento_logico y documento_version quedan separados físicamente. 
15.2 Numeración 
La numeración no reemplaza a la entidad emitida. 
15.3 Regla física 
emision_numeracion mantiene referencia polimórfica a la entidad emitida. 
15.4 Unicidad recomendada 
En numeración, deberá garantizarse unicidad física de: 
 numerador/serie + número emitido 
 
16. Criterio global para motor financiero 
16.1 Raíz física 
La raíz física del circuito es relacion_generadora. 
16.2 Regla congelada 
No se crean como tablas base obligatorias: 
 cuenta_corriente 
 subcuenta_financiera 
16.3 Trazabilidad 
Toda obligación, composición, movimiento y aplicación debe poder reconstruirse desde: 
 relacion_generadora 
 entidad origen del negocio 
 obligados 
 movimientos 
 aplicaciones 
 
17. Criterio global de tipos SQL recomendados 
Esto es preliminar y después lo refinamos por motor objetivo. 
17.1 IDs 
 BIGINT 
17.2 Códigos y estados 
 VARCHAR(50) o VARCHAR(100) según caso 
17.3 Nombres 

 VARCHAR(150) / VARCHAR(255) 
17.4 Descripciones y observaciones 
 TEXT 
17.5 Fechas 
 DATE 
17.6 Fecha/hora 
 TIMESTAMP 
17.7 Booleanos 
 BOOLEAN 
Si el motor no lo soporta nativamente, se adapta luego. 
17.8 Importes / decimales 
 DECIMAL(18,2) o mayor según tabla financiera 
 para índices/cotizaciones podría usarse más escala 
 
18. Criterio global de índices maestros 
18.1 Índices obligatorios 
Toda FK debe tener índice. 
18.2 Índices casi obligatorios 
 todos los codigo_* 
 todos los discriminadores polimórficos con su ID 
 op_id 
 campos de vigencia consultados frecuentemente 
 estados de tablas muy operativas 
 combinación sucursal/instalación cuando se consulte mucho 
18.3 Índices típicos 
 (tipo_relacion, id_relacion)

4. Lectura estructural del bloque 
4.1 sucursal 
Es la cabecera operativa global. 
4.2 instalacion 
Depende de sucursal. 
Una sucursal puede tener varias instalaciones. 
4.3 sincronizacion_paquete 
Representa un lote emitido desde una instalación origen. 
4.4 sincronizacion_operacion 
Representa cada operación individual dentro del paquete. 
Acá queda materializado op_id como identificador único distribuido. 
4.5 sincronizacion_recepcion 
Representa la recepción de un paquete por una instalación destino. 
4.6 conflicto_sincronizacion 
Representa conflictos detectados a nivel de operación. 
 
5. Decisiones físicas que quedan congeladas en este bloque 

5.1 op_id único 
Se congela como UNIQUE en sincronizacion_operacion. 
5.2 paquete + orden 
También se congela UNIQUE (id_sincronizacion_paquete, orden_en_paquete). 
5.3 recepción por destino 
Se congela una sola recepción por combinación: 
 paquete 
 instalación destino 
5.4 sin cascadas destructivas 
No hay ON DELETE CASCADE en estas tablas. 
 
6. Pendientes técnicos de este bloque 
Todavía quedan fuera, a propósito: 
6.1 Checks de dominio 
Ejemplos: 
 estado_sucursal 
 estado_instalacion 
 estado_paquete 
 estado_operacion

6.2 Reglas especiales 
Ejemplos: 
 una sola instalación principal por sucursal 
 no permitir instalación activa en sucursal dada de baja 
 consistencia entre paquete cerrado y cantidad real de operaciones 
 recepción confirmada solo si no quedan errores bloqueantes 
6.3 Payload 
payload_operacion quedó como TEXT. 
Después se puede cambiar a JSON/JSONB si definimos motor objetivo.

3. Lectura estructural del bloque 
3.1 persona 
Es la tabla raíz del sujeto del dominio. 
Soporta tanto: 
 personas humanas 
 personas jurídicas 
Por eso quedaron columnas que sirven para ambos casos: 
 apellido, nombre 
 razon_social 
 nombre_fantasia 
Más adelante, si quisieras extremar normalización, eso podría separarse, pero no lo haría 
ahora porque no fue el criterio congelado. 
 
3.2 persona_documento 
Permite varios documentos por persona, con uno eventualmente principal. 
Ejemplos: 
 DNI 
 CUIT 
 pasaporte 
 documento extranjero 
 
3.3 persona_domicilio

Ejemplos:

 legal

 comercial

3.4 persona_contacto 
Permite múltiples contactos. 
Ejemplos: 
 teléfono 
 celular 
 email 
 WhatsApp 
 contacto alternativo 
 
3.5 persona_relacion

Ejemplos: 
 cónyuge 
 socio 
 garante relacionado 
 apoderado informal 
 familiar 
 relación comercial auxiliar

3.6 representacion_poder 
Modela la representación formal entre: 
 representado 
 representante 
Con vigencia y estado propio. 
 
3.7 rol_participacion

3. Lectura estructural del bloque 
3.1 desarrollo 
Es agrupador inmobiliario opcional. 
No todo terreno tiene que pertenecer a un desarrollo. 
3.2 terreno 
Es la raíz física operativa del núcleo inmobiliario. 
Todo lo inmobiliario termina anclando en terreno, directa o indirectamente. 
3.3 unidad_funcional 
Depende obligatoriamente de terreno. 
No existe unidad funcional sin terreno. 
3.4 edificacion 
Puede estar asociada a: 
 un terreno 
 una unidad funcional 
Pero no debería quedar asociada a ambos simultáneamente en un caso válido. 
Eso queda como restricción XOR pendiente. 

3.5 servicio 
Es catálogo operativo reutilizable de servicios. 
3.6 terreno_servicio y unidad_funcional_servicio 
Materializan la asociación de servicios a cada nivel. 
3.7 disponibilidad 
Registra estado de disponibilidad del objeto inmobiliario con patrón XOR: 
 id_terreno 
 id_unidad_funcional 
3.8 ocupacion 
Registra ocupación del objeto inmobiliario, también con patrón XOR. 
3.9 desarrollo_sucursal 
Materializa el alcance del desarrollo por sucursal. 
3.10 terreno_sucursal 
Materializa el alcance del terreno por sucursal. 
Y por criterio congelado, las entidades derivadas heredan de ahí; no se crea por ejemplo: 
 unidad_funcional_sucursal 
 edificacion_sucursal 
como tablas base obligatorias. 
 
4. Decisiones físicas que quedan congeladas en este bloque 
4.1 desarrollo opcional 
terreno.id_desarrollo queda nullable. 
4.2 unidad_funcional obligatoriamente dependiente de terreno 
id_terreno NOT NULL. 
4.3 Sucursal materializada solo en raíces de alcance 
Queda congelado que el alcance por sucursal se materializa físicamente solo en: 
 desarrollo_sucursal 
 terreno_sucursal 
4.4 Servicio reutilizable 
servicio queda desacoplado del terreno o de la UF. 
 

5. Pendientes técnicos de este bloque 
Todavía quedan afuera, a propósito: 
5.1 XOR 
Hay varias tablas donde debe exigirse “exactamente uno”: 
edificacion 
 id_terreno 
 id_unidad_funcional 
disponibilidad 
 id_terreno 
 id_unidad_funcional 
ocupacion 
 id_terreno 
 id_unidad_funcional 
Eso lo vamos a resolver en la etapa de restricciones especiales con CHECK. 
5.2 Unicidades de vigencia 
Todavía no se resolvió formalmente: 
 una sola disponibilidad vigente incompatible por objeto 
 una sola ocupación vigente incompatible por objeto

3. Lectura estructural del bloque 
3.1 reserva_venta 
Es la etapa previa eventual de una venta. 
No toda reserva tiene que convertirse en venta, pero una venta puede provenir de una 
reserva. 
3.2 venta 
Es la entidad comercial madre. 
Acá no metemos todavía: 
 participantes 
 instrumentos 
 plan financiero 
 documentos 
Solo la cabecera comercial. 
La relación con reserva_venta queda opcional, y además 1:1 práctico, porque puse: 
 UNIQUE (id_reserva_venta) 
Eso responde al criterio que veníamos usando: una misma reserva no debe materializar 
múltiples ventas. 
3.3 venta_objeto_inmobiliario 
Materializa el carácter multiobjeto de la venta. 
Usa patrón XOR: 
 id_terreno 
 id_unidad_funcional 
Todavía no le agregué el CHECK XOR; queda para la etapa de restricciones especiales. 
3.4 instrumento_compraventa 
Representa el instrumento jurídico/comercial derivado de la venta. 
Ejemplos: 

 boleto 
 adenda 
 instrumento complementario 
 escritura comercialmente tratada, si después se mantiene así en tu modelo 
documental/comercial 
La regla importante es: 
 pertenece a una venta 
 no reemplaza a la venta 
3.5 instrumento_objeto_inmobiliario 
Permite que el instrumento cubra: 
 todos los objetos de la venta 
 o solo algunos 
Eso era una regla importante del modelo y acá queda respetada. 
3.6 cesion 
Representa cesiones vinculadas a una venta. 
No reescribe la venta; la referencia. 
3.7 escrituracion 
Representa el acto de escrituración vinculado a la venta. 
Tampoco reemplaza la venta. 
3.8 rescision_venta 
Representa la rescisión o finalización anormal de la venta. 
 
4. Decisiones físicas que quedan congeladas en este bloque 
4.1 venta como raíz comercial 
Todas estas tablas dependen de venta. 
4.2 multiobjeto explícito 
La venta multiobjeto queda físicamente resuelta por: 
 venta_objeto_inmobiliario 
4.3 instrumento separado de venta 
El instrumento no se fusiona dentro de venta. 
4.4 cobertura parcial de instrumento 

Queda resuelta por: 
 instrumento_objeto_inmobiliario 
4.5 reserva opcional 
id_reserva_venta nullable en venta. 
 
5. Pendientes técnicos de este bloque 
Todavía quedan afuera, a propósito. 
5.1 XOR en venta_objeto_inmobiliario 
Debe exigirse: 
 exactamente uno entre id_terreno e id_unidad_funcional 
5.2 unicidades de objeto dentro de venta 
Todavía no se resolvió formalmente impedir duplicados del mismo objeto dentro de una 
misma venta. 
Eso después conviene resolver con restricciones especiales, probablemente separadas por 
terreno/UF o con índice/trigger según motor. 
5.3 cobertura total vs parcial de instrumento 
Todavía no implementé la regla: 
 si instrumento_cubre_toda_venta = TRUE, podrían no ser obligatorias filas en 
instrumento_objeto_inmobiliario 
 si FALSE, deberían existir 
Eso es una regla de negocio/consistencia posterior. 
5.4 cesión y escrituración parciales 
En este bloque solo dejé: 
 es_cesion_total 
 es_escrituracion_total 
Si después querés trazabilidad por objeto cedido o escriturado, probablemente haya que 
agregar tablas detalle específicas. 
Eso todavía no lo agregué porque no lo habíamos cerrado como tabla física obligatoria. 
5.5 una sola rescisión efectiva 
Todavía no restringí si puede haber: 
 una sola rescisión vigente por venta 
 o múltiples eventos históricos de rescisión 
Eso queda para definición fina.

3. Lectura estructural del bloque 
3.1 reserva_venta 
Es la etapa previa eventual de una venta. 
No toda reserva tiene que convertirse en venta, pero una venta puede provenir de una 
reserva. 
3.2 venta 
Es la entidad comercial madre. 
Acá no metemos todavía: 
 participantes 
 instrumentos 
 plan financiero 
 documentos 
Solo la cabecera comercial. 
La relación con reserva_venta queda opcional, y además 1:1 práctico, porque puse: 
 UNIQUE (id_reserva_venta) 
Eso responde al criterio que veníamos usando: una misma reserva no debe materializar 
múltiples ventas. 
3.3 venta_objeto_inmobiliario 
Materializa el carácter multiobjeto de la venta. 
Usa patrón XOR: 
 id_terreno 
 id_unidad_funcional 
Todavía no le agregué el CHECK XOR; queda para la etapa de restricciones especiales. 
3.4 instrumento_compraventa 
Representa el instrumento jurídico/comercial derivado de la venta. 
Ejemplos: 

 boleto 
 adenda 
 instrumento complementario 
 escritura comercialmente tratada, si después se mantiene así en tu modelo 
documental/comercial 
La regla importante es: 
 pertenece a una venta 
 no reemplaza a la venta 
3.5 instrumento_objeto_inmobiliario 
Permite que el instrumento cubra: 
 todos los objetos de la venta 
 o solo algunos 
Eso era una regla importante del modelo y acá queda respetada. 
3.6 cesion 
Representa cesiones vinculadas a una venta. 
No reescribe la venta; la referencia. 
3.7 escrituracion 
Representa el acto de escrituración vinculado a la venta. 
Tampoco reemplaza la venta. 
3.8 rescision_venta 
Representa la rescisión o finalización anormal de la venta. 
 
4. Decisiones físicas que quedan congeladas en este bloque 
4.1 venta como raíz comercial 
Todas estas tablas dependen de venta. 
4.2 multiobjeto explícito 
La venta multiobjeto queda físicamente resuelta por: 
 venta_objeto_inmobiliario 
4.3 instrumento separado de venta 
El instrumento no se fusiona dentro de venta. 
4.4 cobertura parcial de instrumento 

Queda resuelta por: 
 instrumento_objeto_inmobiliario 
4.5 reserva opcional 
id_reserva_venta nullable en venta. 
 
5. Pendientes técnicos de este bloque 
Todavía quedan afuera, a propósito. 
5.1 XOR en venta_objeto_inmobiliario 
Debe exigirse: 
 exactamente uno entre id_terreno e id_unidad_funcional 
5.2 unicidades de objeto dentro de venta 
Todavía no se resolvió formalmente impedir duplicados del mismo objeto dentro de una 
misma venta. 
Eso después conviene resolver con restricciones especiales, probablemente separadas por 
terreno/UF o con índice/trigger según motor. 
5.3 cobertura total vs parcial de instrumento 
Todavía no implementé la regla: 
 si instrumento_cubre_toda_venta = TRUE, podrían no ser obligatorias filas en 
instrumento_objeto_inmobiliario 
 si FALSE, deberían existir 
Eso es una regla de negocio/consistencia posterior. 
5.4 cesión y escrituración parciales 
En este bloque solo dejé: 
 es_cesion_total 
 es_escrituracion_total 
Si después querés trazabilidad por objeto cedido o escriturado, probablemente haya que 
agregar tablas detalle específicas. 
Eso todavía no lo agregué porque no lo habíamos cerrado como tabla física obligatoria. 
5.5 una sola rescisión efectiva 
Todavía no restringí si puede haber: 
 una sola rescisión vigente por venta 
 o múltiples eventos históricos de rescisión 
Eso queda para definición fina. 

 
6. Índices importantes ya incluidos 
Quedaron índices para: 
 cabeceras por estado y fecha 
 navegación venta → objetos 
 navegación venta → instrumentos 
 navegación instrumento → objetos cubiertos 
 venta → cesión / escrituración / rescisión 
 
7. Observación importante sobre cesión y escrituración 
En este punto hay una decisión que más adelante conviene cerrar a nivel físico: 
si cesion y escrituracion van a necesitar también tablas detalle por objeto, por ejemplo: 
 cesion_objeto_inmobiliario 
 escrituracion_objeto_inmobiliario 
Hoy no las agregué porque en lo que cerramos hasta ahora estaba claro que: 
 dependen de venta 
 pueden ser totales o parciales 
pero no quedó todavía congelado como tabla física obligatoria el detalle por objeto. 
Antes de meter tablas de más, prefiero mantener el núcleo prolijo.

3. Lectura estructural del bloque 
3.1 concepto_financiero 
Es el catálogo operativo financiero para identificar componentes como: 
 capital 
 interés 
 ajuste 
 mora 
 gasto 
 bonificación 
 recargo 
 otros 
No lo mezclo con catálogos administrativos generales porque este concepto pertenece al 
núcleo financiero/transaccional. 
 
3.2 relacion_generadora 
Es la tabla raíz del circuito financiero. 
Acá no pongo FK rígida única a una sola entidad de negocio, porque justamente esta tabla 
debe poder representar distintos orígenes: 
 venta 
 contrato de alquiler 
 otro hecho transaccional que genere deuda o movimiento 
Por eso queda con: 
 tipo_relacion_generadora 
 id_relacion_origen 
Es decir, un patrón polimórfico controlado. 
 

3.3 obligacion_financiera 
Representa cada obligación concreta. 
Ejemplos: 
 cuota 
 cargo 
 obligación puntual 
 saldo documentado 
 obligación derivada de contrato 
Depende de relacion_generadora. 
 
3.4 obligacion_obligado 
Permite asociar una o más personas obligadas a una obligación financiera. 
Esto es importante porque: 
 la participación de negocio no siempre coincide con la responsabilidad financiera 
exacta 
 por eso esta tabla queda separada de relacion_persona_rol 
 
3.5 composicion_obligacion 
Descompone la obligación en componentes. 
Ejemplo: 
 capital 
 ajuste 
 interés 
 punitorio 
Esto mantiene el diseño robusto que ya habíamos congelado. 
 
3.6 movimiento_financiero 
Representa el hecho económico registrado: 
 cobro 
 pago 
 nota de crédito 

 reversión 
 imputación base 
 etc. 
Puede o no venir directamente asociado a una relacion_generadora, por eso dejé: 
 id_relacion_generadora nullable 
 
3.7 aplicacion_financiera 
Es la tabla clave de cancelación/aplicación. 
Vincula: 
 un movimiento financiero 
 una obligación financiera 
 opcionalmente una composición específica 
Esto permite: 
 cancelar total o parcialmente 
 aplicar a una obligación completa 
 aplicar a un componente concreto 
 
3.8 cuenta_financiera 
Representa cuentas operativas reales: 
 caja 
 banco 
 billetera 
 cuenta recaudadora 
 etc. 
No representa cuenta corriente conceptual de cliente. 
 
3.9 movimiento_tesoreria 
Representa la materialización de tesorería de un movimiento financiero en una cuenta 
concreta. 
Esto mantiene separadas: 
 lógica financiera 

 lógica de caja/banco 
 
3.10 conciliacion_bancaria 
Agrupa una conciliación sobre una cuenta financiera y un período. 
3.11 detalle_conciliacion 
Descompone la conciliación en movimientos / registros conciliados o pendientes.

4.1 relacion_generadora como raíz física

4.2 cuenta_corriente no se materializa

4.3 subcuenta_financiera no se materializa 
No se crea tabla subcuenta_financiera. 
4.4 obligación ≠ movimiento 
La deuda y el cobro/pago quedan separados estructuralmente. 
4.5 aplicación como tabla propia

 aplicacion_financiera

4.6 composición separada 
La obligación se puede desagregar por concepto sin romper la obligación madre.

5.3 Asociación principal en documento_entidad

5.4 Emisión única por entidad

 renumeraciones

5.5 Serie activa

5.6 Actualización de ultimo_numero_emitido

 por trigger 
 por procedimiento transaccional

5.4 Valores tipados de parámetro

según tipo. 
5.5 Jerarquía de catálogo 
Todavía no forcé: 
 mismo catálogo entre padre e hijo 
 no ciclos 
 no padre = hijo 
5.6 Objeto auditado 
objeto_auditado sigue con referencia lógica: 
 nombre_entidad_auditada 
 id_registro_auditado 
sin FK rígida global única.

4. Reglas de vigencia no superpuesta 
Estas no suelen cerrarse solo con CHECK. 
Lo normal es: 
 índice parcial en casos simples 
 trigger en casos más complejos 
 o control de aplicación muy controlado 
Para este sistema, mi recomendación es: 
 documentar la regla 
 implementar por trigger en tablas históricas críticas 

 
4.1 Tablas con no-superposición recomendada 
 usuario_persona 
 usuario_sucursal 
 rol_seguridad_permiso 
 usuario_rol_seguridad 
 usuario_rol_sucursal 
 denegacion_explicita 
 valor_parametro 
 desarrollo_sucursal 
 terreno_sucursal 
 persona_documento 
 persona_domicilio 
 persona_contacto 
 representacion_poder 
 persona_relacion 
 condicion_economica_alquiler 
 ajuste_alquiler 
 jerarquia_item_catalogo cuando use vigencia 
 
4.2 Regla general de no-superposición 
Para una misma clave lógica, no puede haber dos tramos que se superpongan temporalmente 
si ambos representan vigencia activa incompatible. 
 
4.3 Ejemplo lógico 
En usuario_sucursal, para el mismo: 
 id_usuario 
 id_sucursal 
no debería haber dos filas vigentes superpuestas si significan el mismo vínculo activo. 
 
4.4 Estrategia recomendada 

Definir una función o trigger genérico por patrón de vigencia, según motor.

11. Estrategia de implementación recomendada 
Acá conviene ser muy práctico. 
 
11.1 Lo que sí conviene meter como CHECK directo 
 XOR simples 
 no autorreferencia simple 
 importes/saldos no negativos 
 dominio de ciertos estados o tipos muy cerrados 
 booleanos derivados simples 
 
11.2 Lo que conviene meter con UNIQUE 
 códigos 
 relaciones únicas estructurales simples 
 código de serie 
 código de catálogo 
 login de usuario 
 etc. 
 
11.3 Lo que conviene meter con índices parciales 
 principal único 
 default único 
 vigente único 
 
11.4 Lo que conviene resolver con trigger 
 no superposición de vigencias 
 coherencia sucursal/instalación 
 integridad polimórfica fuerte 

 saldo persistido vs aplicaciones 
 reglas dependientes de otra tabla 
 “tipo de evento exige objeto/detalle” 
 
11.5 Lo que conviene resolver en lógica transaccional de aplicación 
 secuencias complejas de numeración 
 publicación documental 
 cambios masivos con auditoría 
 sincronización distribuida 
 cierre financiero/locativo/comercial de alto nivel
